# リマインダーアプリ 要件定義書（ドラフト v0.2）
---

## 1. 概要

### 1.1 目的
スマートフォン（Android）と Web ブラウザ（React）から使えるリマインダー兼単語学習アプリを構築する。
共有バックエンドを Kotlin + Spring Boot で実装し、DDD・オニオンアーキテクチャを忠実に実践する。

### 1.2 提供価値
- 自然言語でリマインダーを登録でき、曖昧・相対的な時間表現（「明日の9時」「30分後」など）も解釈する。
- 覚えたい単語・問題を定期通知で繰り返し想起させ、記憶の定着を助ける。
- Webでは実現しづらい通知機能を存分に活かす
- 1ユーザーのデータをバックエンドで一元管理し、複数クライアントから利用できる。

### 1.3 実装優先度
- **バックエンド ＞ Android ＞ Web** の順で優先して実装を行う。
- Web 版は「バックエンドを常時利用可能にしておく」ための薄い副次クライアントと位置づけ、実装優先度は低い。通知は持たず、登録・編集・削除のみを提供する。
- 当面の主たる利用形態は「単一端末の Android アプリ＋バックエンド」。

## 2. システム全体構成

```
┌─────────────────────┐        ┌──────────────────┐
│ モバイル(Android) ★優先       │        │ Web(React) ☆低優先     │
│  登録 / 編集 / 削除           │        │  登録 / 編集 / 削除      │
│  ローカル保存（オフライン動作）  │        │  通知なし                │
│  通知のスケジュール・発火 ○     │        │                          │
│  学習項目のランダム選出 ○      │        │                          │
└──────────┬──────────┘        └─────────┬────────┘
           │   REST API (HTTPS, JWT)              │
           │   ・データ同期                         │
           │   ・自然言語の解析依頼                  │
           └────────────────┬─────────────────┘
                            ▼
                 ┌──────────────────────────┐
                 │ バックエンド                        │
                 │ Kotlin + Spring Boot               │
                 │ DDD / オニオンアーキテクチャ          │
                 │ 役割: 認証 / データのCRUD・同期 /     │
                 │       自然言語の構造化               │
                 │ （通知・選出の責務は持たない）         │
                 └─────┬──────────────────┬───┘
                       ▼                  ▼
                  ┌─────────┐       ┌──────────────┐
                  │ DB           │       │ LLM API          │
                  │ （永続化）    │       │ (Gemini / Groq)  │
                  └─────────┘       └──────────────┘
```

### 2.1 責務
通知をローカル・オフラインで行うため、以下のように責務を分ける。

| 責務 | 担当 |
|---|---|
| 認証・認可 | バックエンド |
| リマインダー／学習項目のデータ保持・CRUD・同期 | バックエンド（真実の源）＋ モバイルのローカルキャッシュ |
| 自然言語テキストの構造化（LLM 連携） | バックエンド（クライアントは直接 LLM を呼ばない） |
| 通知のスケジューリング・発火 | **モバイル端末（オフラインで動作）** |
| 単語学習項目のランダム選出 | **モバイル端末（通知発火時にオフラインで実行）** |

- バックエンドは唯一の真実の源。データは API 経由で同期する。
- リマインダー作成（自然言語解析）はバックエンド経由のため**作成時はオンラインが必要**。一度同期された後の通知は**オフラインで動作**する。
- LLM 連携はプロバイダ差し替え可能なようにドメインから隔離する。

## 3. 用語定義（ユビキタス言語）

DDD のため、ドメイン語彙を先に固定する。実装の型・クラス名はこの語彙に揃える。

| 用語 | 英名(仮) | 定義                                          |
|---|---|---------------------------------------------|
| ユーザー | User | アプリの利用者。認証単位であり、データ所有の単位。                   |
| リマインダー | Reminder | 指定したタイミングで利用者に通知する予定。タイトルと通知タイミング、有効フラグを持つ。 |
| 通知タイミング | Schedule | リマインダーがいつ発火するか。「一回限り」「毎日」「毎週」「毎月」のいずれか。     |
| 繰り返し種別 | ScheduleType | `ONE_TIME` / `DAILY` / `WEEKLY`/ `MONTHLY`。 |
| 基準時刻 | ReferenceTime | 相対表現（「30分後」等）を絶対日時へ解決する基準となる現在時刻。           |
| 自然言語入力 | NaturalLanguageInput | 利用者が入力した未解析のテキスト。永続化はしない。                   |
| 解析ドラフト | ReminderDraft | LLM 解析後の構造化された下書き。確定前の状態。不足要素を持ちうる。         |
| 収集セッション | IntakeSession | 不足要素を対話で補うための一連のやり取り。                       |
| 学習項目 | StudyItem | 覚えたい単語・問題の1件。「表（提示面）」「裏（解答面）」、有効フラグを持つ。     |
| 学習項目種別 | StudyItemKind | `QA`（質問・回答型）または `TERM`（用語・詳細型）。             |
| 学習通知設定 | StudyNotificationSetting | 単語勉強の通知頻度・時間帯・オンオフのユーザー設定。                  |

- グルーピング（フォルダ・デッキ）は採用しない。リマインダー・学習項目はフラットに扱う。

## 4. アクター

| アクター | 説明 |
|---|---|
| 未認証ユーザー | 未ログイン状態。ユーザー登録・ログインのみ可能。 |
| 認証済みユーザー | ログイン済み。全機能を自分のデータに対してのみ実行できる。 |
| モバイル端末（スケジューラ） | 通知時刻の到来検知・学習項目の選出・通知発火を担う。 |
| LLM サービス | 外部の自然言語解析サービス（Gemini / Groq 等）。 |

## 5. 機能要件

### 5.1 ログイン・ユーザー管理

| ID | 要件                                             |
|---|------------------------------------------------|
| FR-A1 | 利用者はメールアドレス・パスワードでユーザー登録できる（当面はメールアドレス不要）。     |
| FR-A2 | 利用者はメールアドレス・パスワードでログインし、認証トークン（JWT）を取得できる。     |
| FR-A3 | 認証が必要なリソースは、有効な JWT を持つ場合のみアクセスできる。            |
| FR-A4 | 利用者は自分が所有するデータにのみアクセス・操作できる（他ユーザーのデータは参照不可）。   |
| FR-A5 | パスワードはハッシュ化して保存する（平文保存しない）。                    |
| FR-A6 | 同一ユーザーのデータはクライアント間で共有される（バックエンドが真実の源）。         |
| FR-A7 | （任意・余裕があれば）Google による OAuth2 / OIDC ログインを提供する。 |

#### 5.1.1 認証トークン方式（確定）
- **アクセストークンのみ**を採用し、リフレッシュトークンは設けない（実装コスト最小・追加の有料サービス不要）。
- トークンは再ログイン頻度を抑えるため比較的長めの有効期限とする（具体値は設計時に決定）。
- 標準ライブラリ（Spring Security ＋ JOSE 系ライブラリ等）で実現し、外部の有料サービスは用いない。
- トレードオフ: トークンの即時失効・無効化は困難。単一ユーザー所有・個人利用のため当面許容する。将来必要なら短命アクセストークン＋リフレッシュへ拡張可能な形にしておく。

### 5.2 リマインド機能

| ID | 要件                                                              |
|---|-----------------------------------------------------------------|
| FR-R1 | 利用者は自然言語テキストからリマインダーを登録できる。                                     |
| FR-R2 | 登録に最低限必要な要素は「タイトル」と「通知タイミング」。入力に不足する場合、システムは対話により不足要素を質問して補完する。 |
| FR-R3 | 曖昧・相対的な時間表現（例: 「明日の9時」「30分後」）を、基準時刻（現在時刻・JST）を前提に絶対日時へ解決できる。    |
| FR-R4 | システムは解析結果を**確認画面**で提示する。確認は**必須**とし、利用者は確認画面上で内容を編集してから確定できる。   |
| FR-R5 | 確定したリマインダーは、定義された型・形式（構造化データ）で永続化する（5.2.1）。**自然言語の生文は保持しない**。   |
| FR-R6 | 利用者はリマインダーを一覧表示・編集・削除できる。既存リマインダーの**編集は構造化フォーム**で行う（自然言語ではない）。  |
| FR-R7 | 繰り返しは次の4種に対応する（5.2.2）。                                          |
| FR-R8 | 通知タイミング到来時、**モバイル端末がオフラインで通知**する。Web では通知しない。                   |
| FR-R9 | すべてのリマインダーは**有効／無効フラグ**を持ち、削除せず一時停止できる。無効なリマインダーは通知しない。         |

#### 5.2.1 永続化するデータ（構造化）
| 項目                    | 説明                                          |
|-----------------------|---------------------------------------------|
| id                    | リマインダー識別子                                   |
| userId                | 所有ユーザー                                      |
| title                 | タイトル                                        |
| scheduleType          | `ONE_TIME` / `DAILY` / `WEEKLY` / `MONTHLY` |
| date                  | （ONE_TIME時）対象の日にち                           |
| time                  | 通知時刻（時・分）                                   |
| dayOfWeek             | （WEEKLY時）対象曜日                               |
| dayOfMonth            | smallint | NULL, CHECK 1–31 | MONTHLY のみ使用      |
| enabled               | 有効／無効                                       |
| createdAt / updatedAt | 作成・更新日時                                     |

- 次回発火時刻は規則から導出可能なため、端末側で算出する（バックエンドには保持しない）。
- 値オブジェクト・型の最終設計はドメインモデリングで確定する。

#### 5.2.2 繰り返しパターン（確定）
| 種別              | 指定要素    |
|-----------------|---------|
| 一回限り `ONE_TIME` | 月日 ＋ 時刻 |
| 毎日 `DAILY`      | 時刻      |
| 毎週 `WEEKLY`     | 曜日 ＋ 時刻 |
| 毎月 `MONTHLY`    | 日付 ＋ 時刻 |

### 5.3 単語勉強機能

| ID | 要件 |
|---|---|
| FR-W1 | 利用者は学習項目を登録できる。登録形式は2種類: (a) 質問・回答型（`QA`）、(b) 用語・詳細型（`TERM`）。いずれも「表（提示面）」「裏（解答面）」の2要素1組で構成する。 |
| FR-W2 | 利用者は学習項目を一覧表示・編集・削除できる。 |
| FR-W3 | モバイル端末は、有効な学習項目から**ランダムに1件を選出**し、学習通知設定に従って定期的に通知する。選出はオフラインで端末側が行う。 |
| FR-W4 | 利用者は学習通知設定（頻度・オンオフ）を設定できる（5.3.2）。 |
| FR-W5 | 通知には**表（単語・質問）のみ**を表示し、**裏（回答・詳細）は表示しない**。通知をタップしてアプリを開くと裏を閲覧できる。 |
| FR-W6 | すべての学習項目は**有効／無効フラグ**を持つ。無効な項目は選出・通知の対象外とする。 |
| FR-W7 | 選出は純粋ランダムとする（高度な間隔反復(SRS)は初期スコープ外）。 |

#### 5.3.1 永続化するデータ
| 項目 | 説明 |
|---|---|
| id | 学習項目識別子 |
| userId | 所有ユーザー |
| kind | `QA` / `TERM` |
| prompt | 表（質問 または 単語） |
| answer | 裏（回答 または 詳細） |
| enabled | 有効／無効 |
| createdAt / updatedAt | 作成・更新日時 |

#### 5.3.2 学習通知設定（確定）
| 項目 | 値 |
|---|---|
| 通知頻度 | 1日 1回 / 3回 / 5回 から選択 |
| 通知時間帯 | 9:00–21:00（固定） |
| オンオフ | 機能全体の有効／無効 |

- 通知回数に応じて 9:00–21:00 の範囲へ配置する（例: 3回なら午前・昼・夕方に均等配置）。配置時刻の厳密な決め方は設計時に確定する。

### 5.4 自然言語解析（LLM）機能 ※横断的なサポート機能

| ID | 要件 |
|---|---|
| FR-N1 | 入力テキストと基準時刻を受け取り、構造化ドラフト（タイトル・通知タイミング候補・不足要素）を返す。 |
| FR-N2 | 不足している必須要素を特定し、対話の次の質問を導出する。 |
| FR-N3 | 解析に失敗した場合や信頼度が低い場合は、構造化フォームでの手動入力にフォールバックできる。 |
| FR-N4 | LLM は外部サービスとして扱い、ドメインから隔離する（ポートとアダプタで分離し、プロバイダを差し替え可能にする）。 |
| FR-N5 | LLM へ送信する内容に機微情報を含めない（無料枠は学習データに利用されうるため）。 |

## 6. 非機能要件

### 6.1 アーキテクチャ品質
- DDD・オニオンアーキテクチャを忠実に守る。依存方向は presentation / infrastructure → application → domain。domain はフレームワーク非依存。
- 依存方向の逸脱を ArchUnit のテストで継続的に検証する。
- 永続化モデル・API モデル・ドメインモデルを分離し、ドメインへ外部都合を漏らさない。
- バックエンドのドメインに「通知」「選出」の責務を持たせない（これらはモバイル端末の責務）。

### 6.2 セキュリティ
- 通信は HTTPS。認証は JWT。パスワードはハッシュ保存。
- 認可は所有者単位（自分のデータのみ）。
- LLM へ機微情報を送らない。

### 6.3 性能・信頼性
- 想定規模は個人利用・小規模・単一端末。
- LLM 応答には数秒程度の遅延を許容。LLM 障害時は手動入力へ縮退する。
- 通知時刻の許容誤差は数分以内、**可能なら3分以内**を目標とする（端末側の正確な時刻通知機構の選定に影響）。

### 6.4 オフライン・同期
- 一度同期されたリマインダー・学習項目は、端末がオフラインでも通知できる。
- そのため端末はデータをローカルに保持し、オンライン時にバックエンドと同期する。
- 同期方式（取得タイミング・競合解決）は技術検討事項。

### 6.5 時刻・タイムゾーン
- タイムゾーンは **JST 固定**。相対表現は基準時刻（現在時刻）を前提に解決し、絶対時刻として扱う。

### 6.6 テスト方針（既定）
- JUnit5 + MockK を基本とし、永続化は Testcontainers、依存方向は ArchUnit で検証する。

## 7. 前提・制約

- 確定済み技術スタック: Kotlin + Spring Boot（4.1 系を想定）、DDD・オニオンアーキテクチャ、Android、React。
- 主たる利用形態は単一端末の Android アプリ＋バックエンド。通知はローカル・オフライン。
- Web 版は低優先（バックエンドを常時利用可能にするための薄いクライアント）。
- 未確定（別途技術選定で決定）: DB の種類・永続化方法、ビルド構成（単一／マルチモジュール）、API スタイル、モバイルのローカル保存・同期方式、正確な時刻通知機構、JWT 有効期限の具体値、など。
- 自然言語解析は LLM の無料枠（Gemini / Groq 等）を利用。無料枠は上限変動・データ学習の懸念があるため、機微情報を送らない方針とする。

---

## 8. スコープ外（現時点）

- Web 版での通知。
- サーバープッシュ（FCM 等）・サーバー主導のスケジューリング（通知はローカルのみ）。
- 複数端末への同時通知・マルチデバイス前提の設計。
- ユーザー間の共有・コラボレーション。
- 高度な間隔反復アルゴリズム（初期はランダム選出）。
- UI の多言語対応。
- リマインダー／学習項目のグルーピング。

## 9. 確定した決定事項（Q1〜Q13）

| # | 区分 | 決定内容                                        |
|---|---|---------------------------------------------|
| Q1 | リマインド | 繰り返しは「一回限り(日にち+時刻)／毎日(時刻)／毎週(曜日+時刻)/毎月」の4種。 |
| Q2 | 単語勉強 | 通知頻度は1日 1/3/5回から選択、時間帯は9–21時、機能のオンオフ可。      |
| Q3 | 通知 | 単一端末・モバイルのみ。オフライン（ローカル）で通知する。               |
| Q4 | リマインド | 解析結果の確認は必須。確認画面で編集してから確定する。                 |
| Q5 | リマインド | 既存リマインダーの編集は構造化フォーム。                        |
| Q6 | ログイン | メールアドレスを採用。                                 |
| Q7 | ログイン | 実装コスト最小・無料で実現するため、アクセストークンのみ（リフレッシュなし）。     |
| Q8 | 単語勉強 | 通知には表のみ表示。タップでアプリを開き裏を閲覧。                   |
| Q9 | 共通 | グルーピングなし（フラット）。                             |
| Q10 | 共通 | 通知の許容誤差は数分以内、可能なら3分以内。                      |
| Q11 | 共通 | タイムゾーンは JST 固定。                             |
| Q12 | リマインド | 元の自然言語文は保持しない。                              |
| Q13 | 共通 | リマインダー・学習項目の両方に有効／無効フラグを持たせる。               |

### 9.1 今後の技術的検討事項
- DB の種類・永続化方法（前回からの継続検討）。
- ビルド構成（単一／マルチモジュール）、API スタイル・バージョニング。
- モバイルのローカル永続化方式とバックエンド同期（取得タイミング・競合解決）。
- 端末側の正確な時刻通知の実現方式（3分以内目標）。
- JWT 有効期限の具体値。
- LLM プロバイダの確定（Gemini / Groq 等）。
